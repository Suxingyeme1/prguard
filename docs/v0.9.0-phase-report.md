# v0.9.0 phase report: evidence-routed Independent Review

Status: released 2026-08-24.

## Objective

This increment makes Independent Review selective without making an LLM responsible for its own
activation. After an Implementer Fix passes the deterministic Harness, a versioned router binds the
accepted Patch to its Fix and verification Manifests, replays it at the frozen Base Commit, and
derives an auditable recommendation from repository facts.

The product question is narrow: can PRGuard avoid Reviewer latency and token spend on clearly
small, well-supported Fixes while retaining review for evidence gaps and broader impact? The router
does not decide whether code is correct, and it never overrides failed verification or a policy
gate.

## Outcome

Reviewer routing now runs between an accepted Fix and provider construction. The compatible
`always` mode keeps unconditional Independent Review. `shadow` evaluates the same policy while
forcing the effective route to Review. Only explicit `selective` can skip, in which case PRGuard
delivers a byte-identical copy of the already verified Fix Patch and creates no synthetic Review
result.

The implementation uses short-lived detached Base/Candidate worktrees, Git diff statistics,
declared pytest argv targets, Python AST fingerprints, and the existing bounded two-hop caller/test
graph. It executes no repository code. A 30-second logical deadline prevents a late routing result
from skipping Review; cleanup remains best-effort and may finish after that logical boundary. The
AST index retains its existing 2,000-file/20 MB and context-byte limits. Missing, ambiguous,
truncated, unsupported, or failed analysis adds a hard Review factor rather than becoming a low
score.

The contract and test set covers all three modes, backwards-compatible Task loading, narrow-gate
regression routing, lazy provider construction, exact Patch delivery, candidate-controlled tests
and gate files, dependency/build and sensitive paths, unsupported source, invalid AST, a prior
Implementer repair, Issue/prompt and self-report non-interference, recursive Artifact hashing, and
tamper rejection. The release gate passed Ruff, all 198 unit/integration/contract/security tests,
public-evidence verification, and wheel/sdist build checks.

## Modes and compatibility

- `always` preserves the existing Issue-to-PR behavior and reviews every accepted Fix.
- `shadow` calculates the selective recommendation but still runs the Reviewer, retaining paired
  evidence for both recommended routes.
- `selective` follows the recommendation and can deliver the already verified Implementer Patch
  without constructing a Reviewer or repair provider.

The explicit `review` CLI is unchanged: asking PRGuard to review a Candidate Patch still runs the
Reviewer. Routing applies only to the optional review stage after a successful `fix` workflow. Old
Issue-to-PR Task JSON has no routing field and therefore loads as `always`.

## Deterministic evidence boundary

The routing Artifact records the policy version, recommended and effective routes, evidence score
and threshold, individual factors, Patch and Manifest hashes, diff statistics, pytest argv scope,
changed Python symbols, bounded static caller impact, related/reachable test paths, and analysis
limitations. No evaluator defect label or hidden test enters this Artifact.

The score is an activation mechanism, not a probability. Its weights express conservative product
policy: incomplete analysis, candidate-controlled tests or gates, sensitive paths,
dependency/build changes, a prior Implementer repair, uncovered statically reachable tests, broad
change size, and high bounded static fan-in should spend the extra review budget. A low score means
only that none of the versioned activation rules fired strongly enough; it is not evidence that the
Patch is defect-free.

Routing verifies the Fix Manifest, its archived Task/report, the accepted Verification Manifest,
resolved Base Commit, and final Patch SHA-256 before analysis. An integrity mismatch stops the
composed workflow. Analysis failures are different: they are recorded as incomplete evidence and
force Review. The top-level recursive Manifest hashes `review-routing.json`, the delivered Patch,
and all nested Fix/Review artifacts.

Static evidence keeps its existing limitations. Python reflection, dynamic dispatch, generated
code, monkey-patching, dependency injection, and source outside the bounded index can hide real
impact. Pytest argv scope shows what the declared command selected syntactically; it is not
statement or branch coverage and does not prove that every discovered test executed.

## Frozen implementation evidence

The release demonstrates the following contract behavior with frozen recursive Manifests and
path-free public derivatives:

1. compatibility mode routes every accepted Fix to Review;
2. a small source-only Patch with explicit unchanged-test evidence receives a `skip`
   recommendation, while shadow mode still executes Review;
3. the known narrow-gate normalization regression routes to Review because an unchanged statically
   reachable regression test is outside the declared pytest target;
4. an evidence-guided Implementer repair, candidate-controlled test/gate change, sensitive path,
   unsupported source, or incomplete analysis routes to Review;
5. selective skip copies the exact verified Fix Patch and does not initialize Reviewer credentials
   or a repair provider;
6. tampered routing/Patch/verification bindings cannot produce an accepting selective decision.

The [real-repository shadow pair](../evidence/selective-routing/README.md) adds two manually checked
accepted source changes. PrettyTable #474 passed 21 targeted and 338 wider tests; the changed
`_make_table_handler` symbol had two direct and three transitive repository callers, and its only
reachable test file was explicitly selected. The policy recommended `skip` at score 0/5. Humanize
#366 passed 76 targeted and 700 wider tests plus Ruff, but `naturalsize` still reached
`tests/test_i18n.py` outside the targeted argv and remained related to the excluded optional
benchmark file; the policy recommended `review` at score 9/5.

These cases establish orchestration and two policy outcomes, not routing accuracy. Both are clean,
so Humanize is one observed false route while the pair contains no defective denominator for a
false-skip rate. Selective therefore remains an explicit policy choice; `always` is still the
default and `shadow` is the recommended evidence-collection mode.

## Measurement vocabulary

- A **false route** is a `review` recommendation on an evaluator-confirmed clean Fix. It measures
  avoidable cost, not an incorrect Reviewer verdict.
- A **false skip** is a `skip` recommendation on an evaluator-confirmed defective Fix. Only shadow
  or a later paired audit can show whether the Reviewer would have caught the defect.
- A **false block** is `request_changes` from an effective Review of an evaluator-confirmed clean
  Fix. It is charged to Reviewer behavior separately from the routing recommendation.

The two-case v0.8 Reviewer evidence pair remains useful as one confirmed-benefit case and one clean
cost case. It is not enough to estimate a routing threshold or defect probability.

Post-release update (v0.10.1): a live Reviewer later examined the exact source-only PrettyTable
Patch and identified a multi-table width-state regression. A paired Base/Candidate evaluator check
confirmed it. PrettyTable is therefore a False Skip for the frozen `review-routing-v1` policy, not
a clean skip example. The original targeted/wider test results remain factual but were incomplete.

## Next priority

Run the frozen `review-routing-v1` policy in shadow mode over a larger, manually labelled set of
real repository Fixes. Stratify by direct versus repaired Implementer output, targeted versus broad
pytest scope, ordinary versus sensitive paths, complete versus incomplete static analysis, and
small versus high-fan-in changes. Record raw false-route, false-skip, false-block, Reviewer-yield,
Token, latency, and repair counts before considering a repository-level selective default. Do not
add a Diagnostician or a large benchmark platform unless observed failure evidence requires it.
