# v0.10.1 phase report: a real-repository False Skip

Status: implemented 2026-09-02.

Post-release note: v0.10.2 completed the exact-Patch Humanize pair and one controlled PrettyTable
repair. This file preserves the v0.10.1 snapshot; see
[v0.10.2](v0.10.2-phase-report.md) for the superseding scorecard and final-gate evidence.

## Objective

Close the most important v0.10 evidence gap: run an Independent Reviewer against the exact
PrettyTable source-only Patch whose frozen router recommended `skip`, then bind any post-run
evaluator check to the same Base Commit and Patch. Preserve adverse evidence instead of tuning the
policy after seeing the answer.

## Outcome

The exact Patch SHA-256
`454247c1116b68bdaf56ff2b678a550a8c0b8f05e36d873b151d5f1d4262dfa8` was reviewed at Base Commit
`3c80d392d32f48b0ab1e368793ddb751dbe41807` on the unprivileged server environment. Its declared
gate passed 21 targeted tests; the previously frozen wider run had passed all 338 existing tests.

DeepSeek `deepseek-v4-pro` nevertheless returned one P2 finding with `request_changes`: the Patch
fixes ragged-row padding but leaves `max_row_width` shared across consecutive HTML tables. When a
three-column table is followed by a two-column table, the second table gains an empty field and
cell. The review took 216.700 seconds, used 214,763 input and 11,703 output tokens, and made 19
bounded read/navigation calls. Its recursive Manifest payload hash is
`b0701730f4d1ffb56d6cc7fe9a3d0c4e27ba103d336f6878d946d681bd71ab2b`.

The Reviewer finding was not accepted on prose alone. A post-run evaluator replay produced:

| Revision | Second table fields | Second table rows | Check |
| --- | --- | --- | --- |
| Base | `['x', 'y']` | `[['4', '5']]` | passed |
| Candidate | `['x', 'y', '']` | `[['4', '5', '']]` | failed |

The check and observations are stored in a separately hashed evaluator Artifact and were not part
of the Reviewer Task or provider context. This reclassifies the candidate from clean to defective
without rewriting its original targeted or wider test evidence.

## Scorecard effect

Under the unchanged `review-routing-v1` policy, PrettyTable was recommended `skip` at score 0/5.
The confirmed candidate defect therefore makes it a real-repository False Skip. The three-case
scorecard now reports:

- False Route: 1/1 clean accepted Fix;
- False Skip: 1/2 defective accepted Fixes;
- paired Reviewer coverage: 2/3;
- defective cases caught by Reviewer: 2/2 among paired defective cases;
- two confirmed incremental findings;
- 242.849 seconds, 221,665 input tokens, 13,347 output tokens, and one repair round across joined
  Reviewer observations.

These are case counts, not population rates. The scorecard now treats any observed False Skip as an
activation blocker in addition to reporting incomplete paired coverage. Selective Review remains
explicit and must not become the default under this policy.

## Security note

During server monitoring, one process-list diagnostic exposed a DeepSeek credential because it had
been supplied through `env KEY=value command`, which places the assignment in the parent process
argv. The credential did not enter PRGuard Task, report, Patch, or Manifest Artifacts, and the
downloaded raw run passed a provider-key pattern scan. Further model calls were stopped pending
credential rotation. The server runbook now requires inherited environment or a secret manager and
explicitly forbids secret assignments in argv.

## Boundary and next priority

This result proves neither universal Reviewer recall nor that every Review has positive net value.
It does show both sides of the product decision on one exact Patch: deterministic tests missed a
semantic state interaction, the frozen router would have skipped, and an independent read-only
Reviewer supplied a reproducible defect condition.

After credential rotation, complete the exact-Patch Humanize Review to establish the clean-review
denominator. Then perform one controlled PrettyTable replacement repair that resets per-table state
and passes the original targeted gate, the full existing suite, and the new multi-table evaluator
check. Keep `review-routing-v1` frozen until those artifacts are archived; revise policy only as a
new version with replay over the same cases.
